# VS-01 — Project Setup & Authentication

This slice establishes the **foundation of the Mini Leave Management System** and delivers the first complete user journey:

> **User opens the application → logs in → system authenticates the user → role is identified → user reaches the appropriate protected area → user can log out.**

The goal is not to build the whole HRMS. Everything here should be limited to what is necessary to establish authentication and the foundation needed by later slices.

---

## 1. Slice Context

### Business Context

The organization needs authenticated access to the Leave Management System so that employees, managers, and administrators can access only the functionality relevant to their roles.

### User Context

This slice introduces three roles:

* **Employee**
* **Manager**
* **Admin**

## 2. Slice Goal

**Goal:**

> Establish a working authenticated application where users can securely log in, access role-protected routes, and log out.

### Success Criteria

VS-01 is complete when:

* Application starts successfully.
* SQLite database is initialized.
* User records can exist.
* Passwords are stored as secure hashes, not plaintext.
* Login works with valid credentials.
* Invalid credentials are rejected.
* A session is created after successful login.
* Protected routes reject unauthenticated users.
* Role information is available to the application.
* Logout destroys the session.
* Basic authentication tests pass.

Passwords should be stored using a password-hashing algorithm rather than plaintext; OWASP recommends modern adaptive password hashing such as Argon2id, scrypt, or bcrypt.

## 4. Atomic Requirements

### AR-01 — Application Initialization
The system shall start the Go application successfully.

### AR-02 — Database Initialization
The system shall create/connect to the SQLite database.

### AR-03 — User Storage
The system shall store user authentication information.

### AR-04 — User Role
Every user shall have exactly one initial role: `employee`, `manager`, or `admin`.

### AR-05 — Login
The system shall provide a login form.

### AR-06 — Credential Validation
The system shall verify the supplied credentials against the stored credentials.

### AR-07 — Session Creation
The system shall create an authenticated session after successful login.

### AR-08 — Authorization
The system shall prevent users from accessing routes outside their permitted role.

### AR-09 — Logout
The system shall terminate the authenticated session.

### AR-10 — Authentication Errors
The system shall display an appropriate error when authentication fails.

---

## 5. Business Rules

### BR-01 — Valid Credentials
A user can log in only when the supplied credentials match the stored credentials.

### BR-02 — Inactive User
An inactive user cannot log in.

### BR-03 — Role Required
Every authenticated user must have a valid role.

### BR-04 — Authentication Required
Protected routes require an authenticated session.

### BR-05 — Role Authorization
Authentication does not automatically grant access to every feature.

### BR-06 — Logout
After logout, the previous authenticated session must no longer provide access to protected routes.

## 6. Data Context

### User Schema

```text
User
├── id (INTEGER PRIMARY KEY AUTOINCREMENT)
├── username (TEXT UNIQUE NOT NULL)
├── password_hash (TEXT NOT NULL)
├── role (TEXT NOT NULL) -- employee, manager, admin
├── status (TEXT NOT NULL DEFAULT 'active') -- active, inactive
├── created_at (DATETIME DEFAULT CURRENT_TIMESTAMP)
└── updated_at (DATETIME DEFAULT CURRENT_TIMESTAMP)
```

---

## 7. Session Context

### Session Schema / Model

```text
Session
├── id (TEXT PRIMARY KEY) -- UUID / Cryptographic Random Token
├── user_id (INTEGER NOT NULL REFERENCES User(id))
├── expires_at (DATETIME NOT NULL)
└── created_at (DATETIME DEFAULT CURRENT_TIMESTAMP)
```

## 8. Authentication Flow

```text
User → GET /login → Login Page → Enter username & password → POST /login → Verify Credentials → Set Cookie → Redirect /
```

---

## 9. Authorization Flow

```text
Request → Session Middleware (Check Cookie) → Authenticated User → Role Middleware (Check Role) → Access Route / 403 Forbidden
```

---

## 10. Routes

| Method | Route       | Access         | Purpose            |
| ------ | ----------- | -------------- | ------------------ |
| GET    | `/login`    | Public         | Display login      |
| POST   | `/login`    | Public         | Authenticate user  |
| POST   | `/logout`   | Authenticated  | Terminate session  |
| GET    | `/`         | Authenticated  | Authenticated home |
| GET    | `/employee` | Role: Employee | Employee area      |
| GET    | `/manager`  | Role: Manager  | Manager area       |
| GET    | `/admin`    | Role: Admin    | Admin area         |
