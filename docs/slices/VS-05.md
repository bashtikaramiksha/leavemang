# VS-05 — Manager Approval & Rejection

## Summary

VS-05 completes the approval side of the leave workflow.

An authorized Manager can view pending leave requests, inspect the request details, approve or reject a request, and the system updates the employee's leave balance only when the request is approved.

This slice consumes the Pending requests created by VS-04 and produces the final decision that will later be displayed by VS-06.

## 2. Slice Goal

Allow an authorized manager to make a decision on a pending leave request.

### Success Criteria

VS-05 is complete when:
- Manager can see pending leave requests.
- Manager can open request details.
- Manager can approve a request.
- Manager can reject a request.
- Approved requests update Used Days.
- Approved requests reduce Remaining Days.
- Rejected requests do not change the balance.
- A request cannot be approved/rejected twice.
- Unauthorized users cannot approve/reject requests.
- Decision metadata is stored.
- Tests pass.

## 4. Atomic Requirements

- **AR-01 — Pending Requests**: Manager shall be able to view pending leave requests.
- **AR-02 — Request Details**: Manager shall be able to view complete request information before making a decision.
- **AR-03 — Approve Request**: Manager shall be able to approve a pending request.
- **AR-04 — Reject Request**: Manager shall be able to reject a pending request.
- **AR-05 — Status Update**: The request status shall change from `Pending` → `Approved` or `Pending` → `Rejected`.
- **AR-06 — Balance Update**: Approval shall update the employee's used leave balance.
- **AR-07 — Rejection**: Rejection shall not change the employee's leave balance.
- **AR-08 — Reviewer**: The system shall record which manager made the decision.
- **AR-09 — Decision Time**: The system shall record when the decision was made.
- **AR-10 — State Protection**: A request that is no longer pending cannot be approved or rejected again.

## 5. State Machine

```
                    ┌───────────┐
                    │  Pending  │
                    └─────┬─────┘
                          │
                ┌─────────┴─────────┐
                │                   │
             Approve              Reject
                │                   │
                ▼                   ▼
          ┌──────────┐        ┌──────────┐
          │ Approved │        │ Rejected │
          └──────────┘        └──────────┘
```

Only these transitions are allowed:
- `Pending` → `Approved`
- `Pending` → `Rejected`

---

## 6. Business Rules

- **BR-01 — Manager Authentication**: Only authenticated users with manager authorization can make approval decisions.
- **BR-02 — Pending Only**: Only requests with `status = Pending` can be approved or rejected.
- **BR-03 — Approval Deducts Balance**: When a request is approved:
  `Used Days = Used Days + Request Days`
  `Remaining Days = Allocated Days - Used Days`
- **BR-04 — Rejection Doesn't Deduct**: Rejection does not modify leave balance.
- **BR-05 — Reviewer Required**: Every approval or rejection must record the manager who made the decision.
- **BR-06 — Decision Timestamp**: The system records `reviewed_at` when a decision is made.
- **BR-07 — No Double Approval**: If a request is already approved, another approval attempt must fail.
- **BR-08 — No Double Rejection**: If a request is already rejected, another rejection attempt must fail.

---

## 7. Important Concurrency & Transaction Rule

The approval operation must verify that the request is still pending as part of the state-changing operation:

```sql
UPDATE leave_requests
SET status = 'Approved', reviewed_by = ?, reviewed_at = CURRENT_TIMESTAMP
WHERE id = ? AND status = 'Pending'
```

If no row is updated, the request was already processed.
For the balance update, use a database transaction so the request decision and balance change succeed or fail together.

## 9. Acceptance Tests

- **AT-01 — View Pending Requests**: Pending requests are displayed to manager.
- **AT-02 — Approve Request**: Status becomes Approved, used balance increases by requested days, reviewer & timestamp stored.
- **AT-03 — Reject Request**: Status becomes Rejected, rejection reason stored, balance unchanged.
- **AT-04 — Double Approval**: Second approval fails, balance not changed again.
- **AT-05 — Approve Rejected Request**: Operation rejected.
- **AT-06 — Employee Cannot Approve**: Non-manager access denied (HTTP 403).
- **AT-07 — Insufficient Balance During Approval**: Approval fails if remaining balance < request days, request stays Pending.
- **AT-08 — Transaction Consistency**: Rollback on database failure ensures consistency.
- **AT-09 — Concurrent Approval**: Simultaneous approvals permit only one success.
