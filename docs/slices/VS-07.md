# VS-07 — Leave Notifications

## Summary
VS-07 adds in-app notifications to the leave management workflow. When an employee submits a leave request or a manager approves or rejects it, the target user receives a notification and can view their notification history.

This slice consumes events/state changes from VS-04 and VS-05 without changing the core leave request approval workflow.

---

## 1. Slice Context
```
VS-04 (Employee Applies Leave) ── New Pending Request ──► VS-07 Notifications ──► Manager notified
VS-05 (Manager Approves/Rejects) ── Decision ──────────► VS-07 Notifications ──► Employee notified
```

---

## 2. Success Criteria
- Manager is notified when an employee submits a leave request.
- Employee is notified when their leave request is approved.
- Employee is notified when their leave request is rejected (with rejection reason).
- Notifications are stored in SQLite database (`notifications` table).
- Users can view their notification history.
- Users can mark individual notifications or all notifications as read.
- Unread notification count is available and dynamically updated via HTMX.
- Duplicate notifications are prevented where required.
- User isolation is strictly enforced (Users only see their own notifications).
- Existing leave workflows (VS-04, VS-05) continue working independently.
- Tests pass.

---

## 3. Atomic Requirements
- **AR-01 Notification Creation**: The system creates notifications for defined leave events.
- **AR-02 Manager Notification**: When an employee submits a leave request, the manager receives a notification.
- **AR-03 Approval Notification**: When a manager approves a request, the employee receives a notification.
- **AR-04 Rejection Notification**: When a manager rejects a request, the employee receives a notification with the rejection reason.
- **AR-05 Notification List**: Users can view their notification history.
- **AR-06 Read Status**: Users can mark notifications as read (setting `is_read = true` and `read_at` timestamp).
- **AR-07 Unread Count**: Users can see the number of unread notifications.
- **AR-08 Ownership**: Users can only see notifications belonging to their own `user_id`.
- **AR-09 Notification Link**: A notification links to the relevant leave request.

---

## 4. Business Rules
- **BR-01 Correct Recipient**: Submit -> Manager; Approved/Rejected -> Employee.
- **BR-02 Notification Ownership**: A user can only view/mark notifications matching their `user_id`.
- **BR-03 Read State**: New notifications are `is_read = false`. After marking read, `is_read = true`.
- **BR-04 Read Timestamp**: When marked read, `read_at = current timestamp`.
- **BR-05 Reference**: Notifications reference `reference_type = 'leave_request'` and `reference_id = <request_id>`.
- **BR-06 Historical Notifications**: Notifications are preserved when leave request status changes.

---

## 5. Routes
- `GET /notifications`: List user notifications page
- `POST /notifications/{id}/read`: Mark single notification as read
- `POST /notifications/read-all`: Mark all user notifications as read
- `GET /notifications/unread-count`: Returns HTMX unread badge component

---

## 6. Acceptance Tests (AT-01 to AT-09)
- **AT-01**: Employee submits leave -> Manager receives notification.
- **AT-02**: Manager approves leave -> Employee receives approval notification.
- **AT-03**: Manager rejects leave -> Employee receives rejection notification with reason.
- **AT-04**: New notification created with `is_read = false`.
- **AT-05**: Marking notification read updates `is_read = true` and populates `read_at`.
- **AT-06**: User isolation: User A cannot view User B's notifications.
- **AT-07**: Unread count returns exact count of unread notifications.
- **AT-08**: Mark All Read sets all notifications to read and unread count to 0.
- **AT-09**: Notification references leave request ID and provides navigation link.
